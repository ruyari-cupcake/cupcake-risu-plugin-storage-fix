# 🧁 컵케익 리스 플러그인 저장소 고치기 (cupcake-risu-plugin-storage-fix)

리스(RisuAI) 웹에서 플러그인 저장소가 `Failed to load plugin storage index` 오류로 영영 열리지 않을 때,
**리스 탭 안에서** 상태를 확인하고 고쳐 주는 북마클릿 / 콘솔 스크립트입니다.

**👉 설치 안내: <https://ruyari-cupcake.github.io/cupcake-risu-plugin-storage-fix/>**

## 왜 필요한가

- 리스는 플러그인 저장소(`risuai.pluginStorage`)의 작은 값을 콜드 저장소의 **목차 항목 하나**에 모아 두고,
  데이터베이스에는 그 목차를 가리키는 표시 `pluginCustomStorage._coldpluginIndex`만 둡니다
  (`src/ts/process/pluginStorageStore.ts`).
- 목차를 못 읽으면 리스는 일부러 빈 목차로 바꾸지 않고(다음 저장이 진짜 데이터를 덮어쓸 수 있어서) 모든 요청을
  `Failed to load plugin storage index`로 거부합니다. 이 판단은 **매 부팅** 반복되고, 리스에는 복구 메뉴가 없습니다.
- v3 플러그인은 모두 **같은 저장소 한 칸**을 씁니다(플러그인별 칸이 없음). 그래서 목차가 사라지면 모든 플러그인이
  함께 막히고, 특정 플러그인 몫만 골라 지우는 건 구조상 불가능합니다.
- 목차가 사라지는 경로(소스 판독): Risu 계정 로그아웃 / "계정에 저장" 끄기(계정 콜드 저장소를 로컬로 옮기지 않음,
  upstream [#1690](https://github.com/kwaroran/Risuai/issues/1690)), 콜드 항목 없이 복원된 백업, 브라우저 저장소(OPFS) 정리 등.

## 하는 일

1. **진단** — 목차 파일(`coldstorage_<id>.json`, OPFS)을 직접 열어 세 가지로 나눕니다: **없음**(파일 없음), **손상**(압축은 풀리지만
   JSON/형식이 틀림 — 리스도 똑같이 못 읽음), **불확실**(잠김·읽기 오류·압축 해제 실패 등 — 리스의 fflate는 더 너그러워서 읽을 수도 있음).
   정상이거나 불확실하면 아무것도 바꾸지 않습니다.
2. **복구 먼저** — 콜드 저장소에서 살아 있는 예전 목차를 찾아(앞부분만 풀어서 형식 확인 → 전체 검증) 최근 순으로 보여 줍니다.
   고르면 표시를 그 목차로 옮깁니다. 오래된 데이터베이스로 복원돼서 최신 목차가 남아 있는 경우 등에 데이터가 통째로 돌아옵니다.
   되살린 뒤 첫 로드에서 리스가 그 목차의 정리 대상(유예 기간이 지난) 파일을 지우므로, 다른 시점으로 다시 바꾸기는 어렵습니다.
   이 브라우저에 계정 저장을 쓰다 끈 흔적(`localStorage.dosync === 'avoid'`, 로그아웃·동기화 취소 때 설정됨)이 있으면 경고를 띄우고
   후보를 미리 고르지 않습니다 — 최신 데이터가 계정 쪽에 있을 수 있어서입니다.
3. **초기화** — 살아 있는 목차가 없거나 사용자가 원하면, 없는 목차를 가리키는 표시 **하나만** 지웁니다(확인 체크 필요).
   도구는 다른 키(옛 방식 인라인 값·`_coldplugin`), 콜드 파일, safeLocalStorage, 플러그인 IndexedDB 저장소를 건드리지 않습니다.
   옛 방식 인라인 값은 리스가 다음 로드 때 새 목차로 옮깁니다.
4. **저장 확인** — 바꾸기 전에 저장 파일의 표시가 메모리의 고장 난 표시와 같은지 확인합니다(다르면 저장 중이거나 다른 탭과
   상태가 달라서 아무것도 바꾸지 않고 새로고침을 권합니다). 바꾼 뒤에는 세 가지가 모두 맞을 때만 ✅를 띄웁니다:
   - 바꾼 **뒤에 쓰인** 저장(`dbbackup-*` 번호가 바꾸기 전보다 새로움)일 것,
   - 그 저장의 표시가 목표 값이거나, 그사이 플러그인이 만든 **검증된 다음 목차**(파일이 실제로 정상)이면서 **지금 메모리의 표시와 같을 것**,
   - 메모리의 표시가 **2초 동안 더 바뀌지 않았을 것** — 고친 직후 첫 플러그인 호출은 리스가 목차를 곧바로 한 번, 1초 뒤 한 번 더
     새로 쓰기 때문에, 첫 번째 것만 보고 성공이라고 하면 바로 새로고침할 때 두 번째 쓰기가 사라질 수 있어서입니다.

   OPFS 데이터베이스는 리스가 파일 닫기를 기다리지 않아서 새 백업이 보인 뒤 매번 다시 읽습니다.
   **저장 확인은 스스로 포기하지 않습니다**(0.1.1부터). 리스는 "저장 중"이라는 신호를 밖에 주지 않고, 저장 한 번이 몇 분 걸릴
   수도 있어서입니다 — 큰 데이터베이스를 느린 기기에서 쓰거나, 초기화 직후 플러그인이 저장소를 처음 열 때 예전 방식 값이 새
   목차로 옮겨지면 리스가 다음 저장에서 데이터베이스 전체를 다시 인코딩합니다(순정 `coldstorage.svelte.ts` L677-681 →
   `globalApi.svelte.ts` L423-430). 10초가 넘으면 패널이 "⏳ 리스 저장을 기다리는 중이에요 (N초)"로 기다린 시간을 보여 주고,
   저장이 확인되는 대로 ✅를 띄웁니다. **1분째 새 저장이 없으면** 같은 줄에 두 가지를 덧붙입니다: 큰 저장 파일은 한 번 저장하는 데
   몇 분 걸리기도 하니 그대로 두는 게 좋다는 것, 그리고 리스가 **"현재 탭이 비활성화되었습니다"** 안내(다른 리스 탭이 저장을
   가져갔을 때 순정이 띄우는 안내)를 띄웠다면 이 탭은 저장을 멈춘 상태이니 그 안내의 OK(= 새로고침)를 누른 다음 도구를 다시
   실행하라는 것. 기다리는 동안 패널은 새로고침 버튼을 보여 주지 않습니다 — 저장 도중에 새로고침하면 그 저장이 버려지기
   때문입니다. 표시는 이미 바뀌었고 되돌리지 않습니다. 그만 기다리려면 닫기(×)를 누르면 됩니다(바꾼 표시는 그대로).
   ✅는 **도구가 바꾼 표시**가 저장됐다는 뜻입니다. 플러그인이 따로 저장하는 중인 값까지는 리스가 알려 주지 않아서 확인할 수 없으니,
   방금 플러그인을 쓰던 중이었다면 몇 초 뒤에 새로고침하세요.

바꾸기 직전에 표시가 진단 때와 같은지, 여전히 고장인지, 고른 목차가 여전히 유효한지 다시 확인합니다.
아무것도 인터넷으로 보내지 않습니다. 다른 리스 탭을 닫고, 탭을 새로고침한 직후에 실행해야 합니다 — 플러그인 저장소가 이미
이 탭 메모리에 올라와 있으면(세션 도중 파일이 사라진 경우) 그 메모리의 값은 도구가 확인할 수 없습니다(플러그인 샌드박스가 다른 출처라서).

### 지원 범위

| 리스 | 동작 |
|---|---|
| 브라우저 웹 리스 (risuai.xyz 계정 저장 미사용, 직접 올린 웹 빌드, 포크) | ✅ 진단·복구·초기화 |
| Risu 계정 저장 모드 (`accountst=able`) | 🚫 확인만 하고 거부 — 허브가 잠깐 오류만 나도 같은 문구가 나서 고장과 구분할 수 없음 |
| 자체 서버(노드) 리스, 데스크톱(Tauri) 앱 | 🚫 거부 — 저장소가 서버/앱 안에 있음 |
| `http://` 사설 주소처럼 OPFS가 없는 곳, 압축 해제(DecompressionStream)가 없는 옛 브라우저 | 🚫 안내만 — 도구가 파일을 읽을 수 없음 |

유저스크립트는 만들지 않았습니다. 한 번 쓰고 끝나는 수리 도구이고, 리스는 주소가 제각각이라 하나의 `@match`로 정할 수 없습니다.

## 사용법

설치 안내 페이지([온라인](https://ruyari-cupcake.github.io/cupcake-risu-plugin-storage-fix/), `dist/install.html`)에
북마클릿 버튼·짧은 로더 코드·콘솔 스크립트가 모두 있습니다. 빌드 결과물은 `dist/`에 커밋되어 있습니다.

| 형태 | 파일 | 쓰는 법 |
|---|---|---|
| **로더 북마클릿 (모바일 권장, PC도 가능)** | `dist/loader-bookmarklet.txt` (258자) | 북마크 주소로 저장 → 리스 탭에서 실행. GitHub Pages의 `dist/console.js`를 불러옴 (인터넷 필요) |
| 전체 북마클릿 (PC) | `dist/bookmarklet.txt` (약 80 KB) | 북마크바로 끌어다 놓기 → 리스 탭에서 실행. 외부에서 아무것도 불러오지 않음 |
| 콘솔 | `dist/console.js` | 리스 탭의 개발자 도구 콘솔에 붙여넣기 |

실행할 때는 다른 리스 탭을 닫아 주세요. 고친 뒤 **지금 새로고침**을 누르면 되고, risuai.xyz가 "사이트에서 나가시겠습니까?"라고
물으면 새로고침을 누르면 됩니다(도구가 바꾼 표시는 이미 저장된 상태).

## 검증 (2026-11-03, 순정 RisuAI v2026.10.292 = GitHub `ea61945`)

- 단위·번들 테스트 158개 (`npm test`, 게이트 도중 파일 변경 감시 8개 포함), 뮤테이션 67개(저장 확인 등 핵심 62개 + 기다림
  문구 5개) 전부 검출 (`npm run mutate`) — 0.1.1 기준.
- 실기 (`tests/live/drive.mjs`, 헤드리스 크로미움, 순정 정적 웹 빌드, 매번 새 프로필). 저장 대기는 저장 파일의
  `pluginStorage` 블록을 도구와 별개인 파서로 읽어 메모리와 똑같아질 때까지 확인합니다.
  - 정상 프로필: "정상" 표시, 표시 그대로. 계정 모드 플래그: 거부, 표시 그대로.
  - 초기화 (IndexedDB DB / OPFS DB 각각, 저장 위치 확인 포함): 고장 재현(`Failed to load plugin storage index`) →
    초기화 → 패널 새로고침 → 죽은 표시가 돌아오지 않음, 옛 인라인 값 보존, 새 값 쓰기가 다음 새로고침까지 유지.
  - 확인 중 경쟁: 초기화 직후 플러그인이 값을 쓰고, ✅가 뜨자마자 **바로** 새로고침 → 그 값이 남아 있음.
  - 복구: 데이터베이스가 없는 목차를 가리키고 최신 목차는 남은 상태 → 최신 목차가 첫 후보 → 복구 → 새로고침 후 값 그대로.
  - 계정 흔적(`dosync=avoid`): 경고 표시, 후보 미선택, 안 고르고 누르면 아무것도 안 바뀜, 직접 고르면 복구.
  - 다른 탭이 저장을 가져간 상태(순정 `risu-db` 채널): 도구가 `NOT_SETTLED`로 거부하고 아무것도 안 바꿈 → "지금 새로고침" →
    정상 초기화.
  - **시간을 당긴 실행** (호스트 페이지 시계만 앞당김, 순정 코드 그대로): +2시간 뒤 순정이 옛 목차를 스스로 지운 상태에서
    옛 데이터베이스가 돌아온 진짜 고장 → 복구 → +2시간·+27시간 뒤 새로고침에도 값 유지 → 나중에 다시 실행하면 "정상".
    사흘 뒤 콜드 파일이 사라진 고장 → 초기화 → +2시간·+27시간 뒤에도 정상. (대조: 시계를 안 당기면 옛 목차들이 그대로 남음.)
  - 전체 북마클릿·콘솔·짧은 로더(로컬 번들) 모두 같은 결과.
  - **큰 데이터베이스** (채팅 글로 300 MB·500 MB를 채운 실제 저장 파일, `RPF_BULK_MB`; 느린 기기 흉내는 `RPF_CPU_THROTTLE`로
    호스트 페이지 CPU만 늦춤). 시간은 "초기화" 확인 버튼을 누른 때부터 ✅/⚠까지입니다.

    | 데이터베이스 | 상황 | 서버 CPU | CPU 6배 느리게 | CPU 8배 느리게 |
    |---|---|---|---|---|
    | 300 MB, IndexedDB | 초기화 | 5.0초 ✅ | 15.5초 ✅ | — |
    | 300 MB, OPFS | 초기화 | 6.2초 ✅ | — | — |
    | 300 MB, IndexedDB | 확인 중 플러그인이 값을 씀 | 8.2초 ✅ | — | — |
    | 500 MB, IndexedDB | 초기화 | 9.3초 ✅ | — | — |
    | 500 MB, IndexedDB | 확인 중 플러그인이 값을 씀 | — | 66초 ✅ (0.1.0, 한도 직전) | 0.1.0: 78초 ⚠ 헛경보 → **0.1.1: 79초 ✅** |

    0.1.0은 확인을 1분에서 끊어서, 8배에서 ⚠가 떴습니다(안내대로 30초 뒤 새로고침 → 다시 실행하니 "정상", 플러그인이 쓴 값도
    그대로 — 헛경보). 1초 간격 기록을 보니 표시를 바꾼 뒤 **약 61초 동안 리스가 새 백업을 하나도 쓰지 않았습니다**: 초기화 직후
    플러그인이 저장소를 처음 열면서 예전 방식 값이 새 목차로 옮겨졌고, 그 때문에 다음 저장이 500 MB 전체를 다시 인코딩했기
    때문입니다. 그래서 0.1.1은 시간으로 끊지 않고 끝까지 기다립니다(같은 조건 79초 ✅). CPU만 늦췄고 저장 장치는 서버 속도라서,
    실제 저가형 폰은 이보다 느릴 수 있습니다.
  - **저장이 멈춘 경우** (0.1.1, 다른 탭이 저장을 가져가 리스가 이 탭에서 저장을 멈추고 "현재 탭이 비활성화되었습니다" 안내를
    띄움): 10초에 "⏳ 리스 저장을 기다리는 중", 60초에 그 순정 안내를 짚는 문구가 덧붙음(패널에 새로고침 버튼 없음), 그 뒤에도 계속
    기다림(저절로 ⚠/✅ 없음, 저장 파일은 여전히 고장 표시) → 순정 안내의 OK(새로고침) → 다시 실행하면 "고장"(표시가 저장되지
    않았으므로) → 다시 초기화 → ✅, 다른 값 그대로.
- **반복 실행**: 0.1.1 최종 버전에서 전체 게이트 2회(매번 단위 150개 + 뮤테이션 67개 + 실기 13단계 = 시나리오 11개와 로컬·
  risuai.xyz 로더, 전부 통과). 0.1.0 최종 버전에서는 전체 게이트 2회(각 12단계) + 12단계 2바퀴 반복(24/24). 저장 확인 규칙을 고친 뒤로

### 확인하지 못한 것

- 실제 Risu 계정 로그아웃으로 생긴 고장(계정 없음 — 같은 상태를 OPFS 파일 삭제로 재현), 계정·노드 모드에서의 수리(일부러 지원 안 함).
- 파이어폭스·사파리·iOS, 실제 폰. 큰 데이터베이스의 저장 확인 시간은 CPU를 늦춘 크롬으로만 쟀습니다(위 표 — 저장 장치 속도는 흉내 내지 못함).
  저장 한 번이 1분 넘게 걸리는 정상적인 경우에도(위 8배 측정에서 약 61초 동안 새 백업이 없었음) 1분이 지나면 다른 탭 안내를
  짚는 문구가 덧붙습니다 — 리스가 그 안내를 실제로 띄우지 않았다면 그대로 두면 되고, 저장이 끝나는 대로 ✅가 뜹니다.
- risuai.xyz에서의 복구 시나리오(같은 코드 경로이고 정적 빌드에서 확인).
- **플러그인이 따로 저장 중인 값**: ✅는 도구가 바꾼 표시가 저장됐다는 뜻이고, 리스는 플러그인 저장소가 아직 쓰는 중인지 알려 주지
  않습니다. 새로고침 직전 약 1초(목차가 큰 저장소는 최대 15초) 안에 플러그인이 쓴 값은 리스 자체에서도 사라질 수 있습니다
  (순정의 "닫힐 때 저장"이 최선 노력일 뿐이라서). 그래서 방금 플러그인을 쓰던 중이었다면 몇 초 뒤에 새로고침하세요.
- 이 탭 메모리에 이미 올라와 있던 플러그인 저장소(세션 도중 파일이 사라진 경우)의 값은 도구가 확인할 수 없습니다 — 새로고침 직후 실행.
- 확인 도중 리스 데이터베이스 자체가 교체되는 경우(복원·동기화)는 순정 경로에서 재현하지 못했습니다. 그때는 일반 오류와
  "다시 확인"이 뜨고, 다시 확인하면 실제 상태를 다시 진단합니다.

## 개발

```bash
npm test          # 단위·번들 테스트 (node:test, 의존성 없음)
npm run mutate    # 뮤테이션 검사 — 전부 KILLED여야 함
npm run build     # dist/ 생성
STOCK_DIR=… PLAYWRIGHT_MODULE=… bash tests/live/run-all.sh   # 출시 전 전체 게이트 (tests/live/README.md)
```

- `src/core.js` — DOM 없는 핵심 로직 (진단, 후보 찾기, 복구, 초기화, 저장 파일 확인). Node 테스트와 브라우저가 같은 코드를 씁니다.
- `src/ui.js` — 리스 위에 띄우는 패널 (shadow DOM). 줄 끝 주석 금지: 북마클릿이 줄바꿈을 잃어도 동작해야 합니다 (`tests/bundle.test.cjs`).
- 순정 동작 근거와 계약 → `.report/core-contract.md`, 표시를 읽는 순정 코드 목록 → `.report/caller-map.md`.
